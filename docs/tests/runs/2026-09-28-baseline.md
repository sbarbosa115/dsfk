## Findings

1. **"Ver como" listed stale users (IMP-02).** The menu caches the users list for 5 minutes, so a user created
   meanwhile was missing. Fixed: saving a user refreshes that list too (`UserDialog`).
2. **Settings: refused list values marked no field; saved form kept the typed text (SET-01/02).** The API reports
   list items as `budgetWarningPercents[1]`, and `fieldError` only matched exact names. Fixed: `ApiError.fieldError`
   matches items and sub-fields; the form resets to the stored settings after a save. Both with Vitest tests.
3. **Changing your own password signed you out (AUTH-04).** The session kept the old password hash, so the next
   request treated the user as changed. Fixed: the controller refreshes the session's user after the change
   (also for an admin resetting their own password from Usuarios). Functional tests added.
4. **Security, found while preparing the run (USR-07):** an ordinary admin could take over a super admin by
   resetting their password; fixed and recorded in `docs/security/audits/2026-09-28-rebuild-identity.md`.

## Conditions

- The browser automation's screenshots use a narrower frame than the real viewport (1087 vs 1280 px), and the
  profile's password manager draws an overlay over the page and interrupts scripts on the login form. So clicks
  and typing were sent as DOM events (native value setter + `input` event, `button.click()`) instead of mouse
  coordinates; results were read from the rendered page, and `/api/me` checked in a second tab where a script was
  interrupted.
- The screens were run on the Vite dev server; the production build (`make build` → Symfony :18091) was not
  opened in this run.
